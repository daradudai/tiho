# Hush content-script stress results

*Tiho was called Hush when this report was written. Names in it such as `HUSH_OUT`, `data-hush-*` and `hush-lite` are now `TIHO_OUT`, `data-tiho-*` and `tiho-lite`.*

Generated by `node tests/stress/run-stress.mjs` on 2026-10-10 14:44 UTC — AMD Ryzen 9 3950X 16-Core Processor (32 threads), win32 10.0.26200, Chromium new-headless with software compositing, mode: bundle. The machine was shared with other jobs (model training / inference), so absolute numbers carry noise; the A/B design below is built to cancel most of it.

Mock chat pages (`tests/stress/mock/`) render Twitch- / YouTube-shaped rows (the real adapters extract them) from 20k real chat lines (`ml/data/raw`, sampled to the git-ignored `.corpus/`), with injected waves (~1 per 15 s, 4–8 s, 12–25 % of traffic) and 3 % same-user repeats, trim to 150 (Twitch) / 250 (YouTube) rows and auto-scroll after every 25 ms batch (a forced layout, like the real sites). The Hush runtime runs with the real adapters, preset *chill* (hold 250 ms) and a simulated inference Port (25 ms + 0.4 ms/item per batch, keyword scores) — the model itself runs in the offscreen document, off the page main thread. The in-chat bar is mounted only in rows marked *(with bar)*, in the bar A/B and in the soak, so the runtime and the bar are measured separately.

Method: one page per scenario; JIT warm-up (5 s at 200 msg/s), 2 s settle, then 6 cycles of Hush paused / running (6 s each, order alternating, 1 s after every toggle discarded). Deltas are medians of the per-cycle differences.

- **Hush JS** — time inside Hush callbacks (observer, frame, timers) per message, self-measured (cross-origin-isolated timers, ~2 µs/slice bias).
- **Δ main thread** — CDP `TaskDuration` per message, running − paused: Hush JS *plus* the style/layout/paint work its attributes cause (incl. actually hiding/collapsing the filtered share).
- **max slice** — longest single Hush callback. Long tasks (> 50 ms) and frames > 33 ms are page-wide counts (paused / running).
- **latency** — row inserted → final verdict attribute written (p50 / p95), all messages incl. model round-trips.

## Findings

**Targets.** At 100–200 msg/s the main-thread time Hush adds is **0.11–0.17 ms per message** in script + style/layout (stable across cycles) and **0.14–0.26 ms** in total task time (noisier, ±0.2 ms on this shared machine; it also contains painting the ~20 % of rows that are actually hidden/collapsed, which is the point of the product), now with the full decoration layer in the row stylesheet. The longest Hush callback was **≤ 1 ms** (2.4 ms with 4× CPU throttling): Hush never causes a long task. No frame > 33 ms was attributable to Hush at normal CPU speed. Low rates (10–50 msg/s) look worse per message only because fixed per-second costs (1 s housekeeping tick, ≤ 4 Hz store flush) are divided by few messages; in absolute terms it is ~2–8 ms per second.

**End-to-end with the real extension** (`node tests/stress/ext-smoke.mjs`, built with `HUSH_OUT=.output-runtime npx wxt build`, 50 msg/s, real offscreen model `hush-lite/uint8` on WASM): rows on screen decided 147/150 (Twitch) and 248/250 (YouTube) — the rest in flight; insert → verdict latency p50 10 / 30 ms, p95 60 / 62 ms; 0 long tasks, 0 frames > 33 ms.

**What moved the numbers** (measured with this harness while building it):

| change | effect |
|---|---|
| stylesheet: plain attribute selectors instead of `:is(<row selector list>)`, no `+` sibling rule and no CSS counter for pill runs (the runtime marks each run's last row with `data-hush-run=N`, O(changed rows)), no `> *` rule | style recalc +0.55 → +0.10 ms/msg |
| UI decorations (`src/ui/decorations.ts`: category edges, highlight glow, pills, wave badge, hover reason chip) merged into the runtime sheet under the same rules: compound attribute selectors only, accents as per-category custom properties, no transitions on rows | style+layout +0.05 to +0.09 ms/msg at 10–200 msg/s (+0.08 to +0.15 with the bare base sheet before): no extra cost |
| hide-at-birth via one list attribute (`[data-hush-list] > :not([data-hush-a])`) instead of a per-row `pending` premark; held rows get no write at all | one style recalc less per row, no flash even for rows inserted inside the page's own rAF |
| late model verdicts coalesced with the page's next rendering frame (≤ 40 ms, only above 20 msg/s) | Δ main thread −0.15 to −0.25 ms/msg at 100 msg/s |
| no per-frame fallback timer (only while hidden), one sort of ≤ 512 latency samples per tick, SWAR SimHash, regex pre-gates, one attribute read per fresh row | Hush JS ~110 → ~80 µs/msg at 100 msg/s |

**Where the remaining time goes** (in-page, JIT warm, per message): platform adapter `extract()` ≈ 28 µs (largest single item — adapter workstream), rules ≈ 9 µs, waves ≈ 8 µs, normalize + cache + bookkeeping ≈ 20 µs, attribute writes ≈ 5 µs, frame/tick overhead ≈ 10 µs. In-page code runs ~3× slower than the same functions in a hot loop (cold caches between frames), so cutting work matters more than micro-tuning.

**In-chat bar.** Measured on its own with the *bar A/B* (table above: Hush running in both halves, the bar unmounted / remounted in place). Before this round it cost **+4.46 / +0.44 / +0.09 ms per message at 10 / 50 / 150 msg/s** (≈ 45 ms of main thread per second at 10 msg/s, nearly all paint and style); now **+0.17 ms/msg (1.7 ms/s) at 10 msg/s and ≈ 0 at 50 and 150 msg/s** (−0.07 / −0.01: below the noise). With Hush paused vs running and the bar mounted in both halves (*with bar* rows), 10 msg/s went from +5.34 to +0.84 ms/msg (Hush alone: +0.75). Steps, measured with the bar A/B at 10 msg/s:

| change | Δ main thread at 10 msg/s |
|---|---|
| before: activity pulse animating the logo's SVG path (`d` + transform keyframes, main thread, every 700 ms); chips' scroll-driven `mask-image` animation; calm ring easing `stroke-dashoffset` for 400 ms after every 125 ms counter update; view flushed in a rAF of its own | +4.46 ms/msg |
| pulse = cross-fade of two pre-rendered logo images on an HTML layer (opacity, compositor — Chrome does not composite animations of SVG elements); static edge-fade overlays toggled from scroll / resize events; ring without easing; compact row `contain: strict`; store changes applied in the writer's task, so bar updates ride the runtime's frame instead of adding one | +0.39 |
| counters 4 → 2 updates/s; calm % with ±0.75 pt hysteresis (a ratio sitting at x.5 % flipped ring and number on every update); pulse at most every 6 s | +0.26 |
| chip glyphs and the logo as CSS background images instead of inline `<svg>`: each SVG root is a paint chunk of its own (viewBox transform + clip) that the page re-walks and re-layerizes on every frame it paints — a trace showed ~0.6 ms/s of Layerize and ~0.5 ms/s of Paint for the seven chip icons alone | +0.22 (+0.17 in the final full run) |

What is left is mostly per-frame: a trace still attributes ~1 ms/s of Paint to the bar's mere presence (it stays with the row's content hidden), plus the 2 Hz counter repaints. The mock pages render at 60 fps (their frame meter runs a rAF loop), so every per-frame cost is counted 60 times a second here — the conservative case. Running animations cost a little main-thread style work per frame even when composited, which is why the pulse is rare. The *(with bar)* rows above measure Hush paused vs running with the bar mounted in both halves (the bar idles when Hush is paused).

**Decorations and the reason chip.** Seen on real Twitch (logged out, i.e. light theme) and Kick with the built extension, and on the mock chats with `node tests/stress/look.mjs` (real runtime + stylesheet + bar, both site themes; screenshots in `.runs/look/`). The hover chip straddles the row's top edge 44 px from the right: in the gap between messages, clear of the sites' own hover actions (Twitch's reply button sits at the top right, 32 × 32 px), never over the hovered message's text, out of flow.

**Measurement notes.** New-headless Chromium needs `--disable-renderer-backgrounding --disable-backgrounding-occluded-windows` or rAF never fires; with the GPU busy (model training) compositor frames stall, hence `--disable-gpu`. Without cross-origin isolation `performance.now()` is coarsened to 100 µs and inflated the runtime's self-timing of short callbacks ~5×, so the mock pages are served with COOP/COEP. The runtime's own `perf.mainMs` in a real page has the same upward bias.
